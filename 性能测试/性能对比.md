# 魂斗罗性能对比

对比三段日志：

- A：`魂斗罗 内部m68ram+vram titlecache.txt`
- B：`魂斗罗 m68 ram 6页cache +vram 内部ram.txt`
- C：`魂斗罗 优化音频后 m68 ram 6页cache +vram 内部ram.txt`

C 的改动：YM 包按约 64 个 audio sample 提交，事件满/帧尾仍强制提交；Core0 音频后处理按 5 个 32-sample chunk 聚合，也就是约 160 sample 后统一 stretch/pitch/EQ/submit，聚合和后处理 buffer 尽量放 PSRAM。

## 结论

C 的音频优化有效，最核心的变化是 YM 队列反压大幅下降。B 的 `YM block wait` 是 `37.51 ms/s`，C 降到 `11.33 ms/s`；`queue wait` 从 `35.67/s` 降到 `11.19/s`；平均队列最高水位从顶满的 `24.00` 降到 `13.10`。这说明“减少 YM 包数量 + 5 块聚合后处理”确实让 Core0 不再长期追不上。

画面也受益：实际绘制从 `17.29 fps` 到 `18.63 fps`，debug rendered 从 `16.85 fps` 到 `18.30 fps`，fskip 从 `32.03/s` 降到 `30.57/s`。也就是说，这版不是靠空转省 CPU，而是减少音频链路的无效小包开销后，把一部分时间还给了渲染。

需要注意的新副作用是动态调速更积极了：`stretch samples` 从 `242.03` 增到 `297.01`，`stretch ctl` 从 `22.61` 增到 `31.06`，`audio debt` 从约 `-40.0 ms` 变成 `-30.7 ms`。这不是断流，但说明 160-sample batch 让虚拟水位变成更粗的锯齿，控制器在两次 submit 之间更容易判断“水位偏低”，于是加大 stretch。

后续如果继续优化，优先改动态水位控制：把 `batch_count` 纳入有效水位估算，或者在 `vb` 接近低水位时提前 flush batch，而不是立刻加大 stretch。这样能保留 C 的低 YM 等待，同时把 `ctl/str` 拉回 B 附近。

## Z80 和 YM 等待判断

新版本 Z80 略升：`3.64 ms -> 3.73 ms`，幅度只有 `+0.09 ms`。这更像是场景和调度变化带来的正常波动，不是主要瓶颈。

YM 侧变化非常明确：`ym0 4.51 ms -> 3.95 ms`，同时 `ymblk 37.51 ms/s -> 11.33 ms/s`。`ym0` 只统计 YM 包渲染，不完整包含 stretch/pitch/EQ/submit，但队列等待下降说明优化方向是对的。当前更值得盯的是动态调速的过度补偿，而不是 YM 队列本身。
